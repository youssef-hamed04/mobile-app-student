# Student Center — preparing the App Review account

For the administration (who creates and prepares the account) and the iOS
developer (who enters it in App Store Connect). Apple requires a working
sign-in for an app with accounts (guideline 2.1). **Never put the phone number
or password in this repository, a ticket, a chat or an email thread** — they go
only into App Store Connect → App Review Information → Sign-In Information.

Everything below uses features that already exist. Nothing here needs a code
change, and nothing asks the reviewer to pay, redeem a code or activate
anything.

---

## 1. Create a dedicated student account

- Register a **new** student account used for nothing else (no real student's
  account, no staff account). Use a phone number the business controls, so the
  number can receive WhatsApp from support if a reset is ever needed.
- Choose academic details (university, faculty, department, year) that match the
  course(s) you will give it, so the catalogue the reviewer sees is coherent.
- Choose a strong password. If you ever need to change it, use the dashboard:
  **Students → open the account → Reset password** (`PUT /admin/users/:id/password`).
  A reset signs the account out everywhere.

**Do not sign in to this account on any phone or tablet** after registering it
(see section 3). If you registered it from the app on a device, reset its
devices afterwards (section 3).

## 2. Give it representative content — without any payment

Pick one course that has normal lessons with video (and ideally attachments) and
at least one library document. Then use one of these, all done by the
administration before submission:

| Way | How | Notes |
|---|---|---|
| **Direct grant (preferred)** | an administrator calls `POST /api/v1/admin/enrollments/grant` with `{ "userId", "courseId", "accessDurationDays" }` (admin role only; teachers get 403) | no code, no money; recorded as an administrative grant. The dashboard has no button for it today, so it is an API call made with an admin session |
| Access code generated by the administration | create a code for the course in the dashboard (Codes), then redeem it **for the review account on the student website** before submission | the reviewer never sees or types a code; the account simply has the course |
| Free course | choose a course published as free; the reviewer can join it in the app with "Join now" | only if a free course with real video exists |

Library documents: either rely on **preview parts** (readable by everyone), or
give the account the document beforehand through the normal website flow done
by the administration (never ask the reviewer to do it).

**Check before submission** by signing in with the account on the student
website (not the app — see section 3): the course and the document appear, a
video plays, a PDF opens.

## 3. No bound device at submission time

Every account is linked to one device. The backend activates the **first**
device of an account that has no active device automatically
(`DEVICE_AUTO_BIND_FIRST`; production confirmed: 1,063 of 1,064 first devices in
the last 30 days were activated this way). A second device waits for approval,
and **videos do not play on a device waiting for approval**.

So when you submit:

1. The account must have **no active device**. If anyone signed in with it on a
   phone, open **Students → open the account → Device tab → Clear device binding**
   (`POST /admin/devices/users/:userId/reset-binding`) or revoke that device.
2. Apple's reviewer signs in on their device, which becomes the active device.
3. Apple sometimes tests on a **second device** (often an iPad). That device
   appears under **Students → Device requests** (also counted on the dashboard home); approve it there
   (`POST /admin/devices/change-requests/:id/approve`). Keep someone watching
   the requests during the review window (Apple does not announce when it starts).
4. After review, reset the binding again before the next submission.

## 4. What to write in App Store Connect

- **Sign-In Information:** the phone number (as the user name) and the password.
- **Notes:** use the review notes in `APP-STORE-LISTING-DRAFT.md` — they explain
  that access is granted by the administration or the website, that the app
  sells nothing, the one-device rule and that a second device needs approval,
  and why screen recording is blocked.
- **Contact information:** a person who can approve a device during the review.

## 5. Safety

- The account is a normal student: it sees only what was granted to it and has
  no staff rights.
- Its playback is subject to the usual limits (three plays per lesson, see the
  backend). Grant a course with several lessons so a reviewer re-testing does
  not run out.
- Do not change its password during review; Apple would be locked out.
- After the app is approved, keep the account (Apple re-uses it for updates) and
  repeat section 3 before each submission.
